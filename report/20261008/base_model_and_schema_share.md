# 素のモデルで解けたのか、と大規模元問題で落ちる理由（10/8 のご質問への回答）

下沢 亮太郎（2026-10-08）。詳細は `ProgAndSpec/DSPy_Shizuoka_V3_handover/RESCORE_REPORT.md` 36 章。

## 1. 学習の結果か、素のモデルでも解けたのか

**学習の結果です。** 素のモデルに使える手（修復ループ、長い思考、正解に近いコードを見せる）を足しても、ほとんど解けません。

| 条件（大規模生成テスト 120 問） | 正解 |
|---|---:|
| 素の Gemma 4 12B | 0 |
| 素の 12B + 実行・検証・修復 2 回（ハーネス） | 1 |
| 素の 12B + 長い思考（32k token） | 0（全問で出力上限） |
| 素の 12B + 同じ種別の教師の正解コードを 1 本見せる | 11 |
| 素の 4B + 同じ種別の教師の正解コードを 1 本見せる | 15 |
| **学習済み 4B / 12B LoRA / 12B FFT** | **91 / 95 / 99** |

- 「教師コードを見せる」は、学習と同じ知識を重みを変えずに文脈で渡す対照です。それでも 1 割にとどまります。
- 素の 12B は、見せたコードを今の問題に合わせて書き換える段階で制約を崩します。素の 4B は推論が終わらず、同じコメントを
  繰り返して出力上限に達します。

## 2. 学習済みモデル（FFT / LoRA）が間違える問題

- **学習していない種別は 0 問**（乗務員ペアリング、ポートフォリオ 2 種別）。
- **教師コードを丸ごと再現して解いている。** 大規模の教師データは種別ごとに Opus のコードが実質 1 本で、学習済みモデルは
  それをほぼ一字一句そのまま書きます（一致率の中央値 100%）。入力が学習時と少しでも違うと、コードを書き換えにいって
  構文やキーの読み違いを起こします。
- **LoRA は長いコードで出力上限に当たる**（prp は教師コードが 2.3 万字）。FFT では少ない。
- 問題の数学的な難しさで解けない問題は、学習した種別には残っていません。

## 3. 大規模元問題 28 問で落ちていた理由と、その対策

元問題と生成問題は、説明と要件（目的・制約・規模）が一字一句同じで、違うのは数値だけでした。ただ、問題文の末尾に付く
**「返り値の形」の節**だけは、元問題では同梱の参照コードの返り値（途中経過のフィールドなど）から作られていました。
そのため 28 問中 16 問で学習時と形が違い、モデルは覚えたコードの返り値の部分を書き換えて壊していました。

この節だけを学習時と同じ形にそろえて、もう一度解かせました。採点は元の参照解のままで、モデルも変えていません。

| モデル | これまで | 返り値の形をそろえた後 |
|---|---:|---:|
| 12B FFT | 14 | **22** |
| 4B | 10 | **20** |
| 4B + 修復 + 12B フォールバック（3 月の構成） | 12 | **22** |
| 12B（20 種別データ） | 13 | **21** |

- どのモデルでも 8〜11 問増え、減ったのは 1 問だけです。3 月の構成では、12B に回す問題が 18 → 7 に減りました。
- 学習した種別では 22 / 24 まで解けています。残りは乗務員ペアリングとポートフォリオで、20 種別データの学習で取りにいっています。
- 3 月の成果物では、対応する種別ごとに返り値の形を決めておけば済みます。利用者が別の形を求めたときは、決めた形で解いてから
  変換する段をハーネスに足す予定です。

## 4. 自動最適化されたハーネス（Meta-Harness）と GEPA optimize_anything について

- **Meta-Harness**（Lee, Nair, Zhang, Lee, Khattab, Finn、arXiv 2603.28052）は、モデルの周りのコード（何を保存し、
  何を見せるか）を自動で改良します。提案役はコーディングエージェント（Claude Code）で、過去の候補のコード・スコア・実行ログを
  ファイルとして読み、新しいハーネスを書きます。TerminalBench-2 で、Haiku 4.5 では 37.6%（人手で作られた最良の Goose が 35.5%）、
  Opus 4.6 では 76.4%（Terminus-KIRA が 74.7%）でした。著者に DSPy の Khattab 氏が入っていますが、DSPy や GEPA そのものではありません。
- **GEPA の optimize_anything** は、任意のテキスト（複数可）を最適化対象にできます。評価関数がスコアと診断情報を返し、
  それを読んだ LLM が書き換えを提案します。応用の **gskill** は、コーディングエージェント用のスキル文書（.md）を、リポジトリの課題を
  解かせた結果から学習します。いま使っている gepa にも入っています。
- **この研究での位置づけ:** 学習済みモデルの指示文を GEPA で最適化しても、これまで 52 案中 1 案も採用されませんでした。
  学習済みモデルは指示文の書き換えを受け付けないためです。一方、効いた手はどれもモデルの周りにありました。
  - 返り値の形をそろえる：元問題で +8〜11 問
  - 検証器で失敗を見つけて 12B に回す：生成テストで +10 問
- **提案:** 最適化の対象を、指示文からハーネス側のテキストに移します。
  - 対象: 要件を学習時の形にそろえる手順、要求された形への変換、修復の指示、12B に回す条件
  - 評価: 検証器の判定をスコアにし、失敗の分類（構文、データの読み違い、制約違反など）を診断情報として渡す
  - 評価用の問題: 要件の書き方や返り値の形を変えた問題を、学習用の instance から作る（汎化の測定にもなる）
  - 今日見つけた「返り値の形のずれ」は人手で見つけましたが、この仕組みなら自動で見つけて直せるはずです。
  - 費用: 元問題 28 問の評価 1 回が 30 分〜1 時間（4B 単独〜12B フォールバック付き）なので、候補 10〜20 個で GPU 1 枚 1 日前後を想定しています。
