## A. 結果の読み方

**Q1. 大規模テスト 120 問で 93 問というのは、未知の要件を解けるということか。**
違います。120 問は「学習した 20 種別の、数値だけ違う新しい問題」です。種別そのものは学習で見ています。学習データのなかった 3 種別はテスト 18 問中 0 問でした。いま言えるのは「学習した種類の新しい instance なら 9 割弱解ける」までで、「未知の要件を解ける」ではありません。当面は対象を学習した 20 種別に絞り、対応種別を明示して出す方針です。

**Q2. 「正解 = 参照解から +10% 以内」は甘くないか。参照解は最適解か。**
最適解ではありません。大規模問題は厳密解が出ない規模なので、参照解は手持ちの教師コード 95 本（主に Claude Fable が 600 秒で出した解）の最良値です。下界があるのは 4 問だけです。+10% は学習データを選んだときと同じ基準で、「参照解と同等以上」の数も併記しています（全層学習 93 問のうち 81 問）。閾値を 0 / 5 / 10% と変えても条件間の順位が変わらないことは次回までに確かめます。

**Q3. 素の Gemma が 0 問、Qwen3.6 が 4 問というのは低すぎないか。評価の設定が厳しいのでは。**
出力枠 8,192 token、実行上限 900 秒、思考なし（Qwen は思考あり 65k）で測っています。素のモデルが落ちる理由は、小規模問題向けの書き方（全列挙、時間制限なしの厳密ソルバー）をそのまま当てて、制約違反や時間超過になることです。Claude Fable は同じ 28 問で 22 問解けるので、問題が解けないのではなく、小さいモデルの書き方の問題です。学習後はこの書き方が直ります。

**Q4. 12B の LoRA と全層学習の差（88 対 93）は意味があるか。**
統計的には有意ではありません（問題単位の入れ替わりは 8 対 3、p ≈ 0.23）。全層学習は GPU 2 枚と fp32 の主重みが要るので、小型化が目標なら LoRA か 4B で十分という判断です。

**Q5. 4B が 81 問というのは、12B より小さいのにそこまで解けるのか。**
解けます。同じ教師データで学習すると、学習した種類の問題では土台の大きさはほとんど効きません（9 月の 4B と 12B の比較でも同じでした）。差が出るのは長いコードの崩れ（4B は実行時エラー 31 件、12B は 16 件）で、これは修復ループで拾える見込みです。

## B. プロンプト最適化と交互最適化

**Q6. GEPA は結局効いたのか。**
素のモデルには効きました。素の Gemma で進化させた指示文は、学習に使っていない雛形テストで 345 → 364 問（p ≈ 0.04）です。Qwen3.6 に転用しても 4 → 9 問（有意ではない）。一方、学習済みモデルには効きません。3 回の GEPA で 52 案を試して採用 0 でした。

**Q7. なぜ学習済みモデルではプロンプトが動かないのか。**
固定の指示文で 1 万 6 千件を学習したモデルは、その文面に張り付いています。指示文を書き換えると、出力枠を使い切る、構文が崩れる、といった形で壊れます。GEPA の提案はどれも元の指示文より点が低く、採用されませんでした。

**Q8. BetterTogether の論文では相乗効果が出ている。なぜここでは出ないのか。**
論文は素のモデルから始め、プロンプト最適化で得た成功例を学習データにします。ここでは教師データが外部（Claude、Qwen）の検証済み正解で、量も 1 万 6 千件あります。プロンプトで得られる差（数十問）は、教師データの効果（数百問）に埋もれます。同じ順序で素のモデルから回しても、GEPA の指示文で学習したモデルと既定の指示文で学習したモデルは差がありませんでした（89 対 88）。論文の設定（教師データなし、自己生成のみ）に近づければ相乗効果が見える可能性はありますが、それは精度を下げてまで試す価値があるかという判断になります。

**Q9. では柱 2（交互最適化）はやめるのか。**
形を変えて続けます。(1) 学習時に複数の指示文を混ぜて張り付きを弱め、学習後に GEPA が動くかを 4B で 1 本試します。(2) 最適化の対象を「生成 → 検証 → 修復」の修復段に移し、生成段の指示文を壊さずに GEPA を回します。どちらも採用 0 なら、「交互最適化は指示文の固定化で失敗する」という知見として出します。

**Q10. 前回「GEPA の反省の方向を指定できないか」という話があった。どうなったか。**
できるようにしました。反省プロンプトを「複数の問題に共通する一般則だけを書け、約 4,000 字以内」に差し替えています。以前の 34KB の指示文は出なくなり、素の Gemma での指示文は 4,152 字です。

## C. データと手続き

**Q11. 学習データに Claude の出力を使っているが、ライセンスや利用規約は問題ないか。**
研究用途の範囲で、Claude と Qwen の出力を学習データに使っています。商用利用や外部配布の際は各モデルの利用規約の確認が要ります。これは私の判断では決められないので、確認をお願いしたい点です。

**Q12. 学習データとテストデータは本当に分かれているか。**
instance は分かれています。雛形問題は乱数の種、大規模問題は分割で分け、テスト用 instance は学習に一度も使っていません。ただし種別は共通です（Q1）。参照解を作った教師コードの一部は、大規模の元問題 28 問に対して書かれたものなので、元問題 28 問の評価は「教師が見た問題」という意味で準汚染です。

**Q13. 乗務員ペアリングとポートフォリオが学習に入っていなかったのはなぜか。直ったのか。**
乗務員ペアリングは、元問題 2 つで規則が違う（各便ちょうど 1 回か、1 回以上か）のに検証器が両方に重複を許していたため、問題文どおりに解いた正解が「参照より悪い」と判定されていました。ポートフォリオは、問題文の要約が 300 × 1,200 の行列をそのまま書き出して 4 万 token になり、学習の最大長を超えていました。どちらも直し、20 種別すべてに学習データが入った状態で 4B を学習し直しています。

**Q14. 評価の数字は再現するか。**
実行時間に依存する部分があります。大規模問題の解答は時間制限付きのソルバーを使うので、CPU が混んでいると解の質が落ち、+10% の判定が変わることがあります。実際に、他のジョブと同時に学習データを作り直したところ、同じコードでも 41 件が不正解側に変わりました。評価と判定は CPU の空いているときに流す運用にしました。

**Q15. GLM を使わない理由は速度だけか。**
速度です。320B のモデルを H200 2 枚に載せると一部が RAM に溢れ、約 14 token/秒でした。1 問に思考だけで 2 万 token 以上使うので、1 問 40 分かかり、3 問で正解 0 でした。量子化を 4 bit まで落とせば GPU に収まり速くなる見込みはありますが、教師データは Claude で足りているので優先度を下げました。

## D. 3 月に向けて

**Q16. 3 月に何を見せるのか。**
4B のモデルに、サンドボックス実行、20 種別の検証器、修復ループを組み合わせた一体のデモで、持ち込みの問題をその場で解くことを目標にします。評価は「学習種別の新しい instance」「学習から外した種別」「封印問題」の 3 層で出します。

**Q17. 封印問題とは何か。なぜ必要か。**
DENSO 側に、発表まで非公開の問題を 5〜10 問ご用意いただき、評価の手順（検証器、時間上限）を事前に合意しておくものです。こちらで作った問題だと「学習に似た問題ではないか」という疑いが残るので、評価者が出した問題で測るのがいちばん信頼されます。企業の実績データを取り込む入口にもなります。

**Q18. 大きな AI を直接使うのと比べて、小型モデルにする利点は何か。**
数字の表はまだ作っていません（次回までに用意します）。わかっている範囲では、4B は 120 問を 1 時間弱で解き、1 問あたりの出力は 3 千 token 前後です。Claude Fable は 1 問 10 分かけて解いています。精度は Fable が上（28 問で 22 対 10）なので、「速くて安い代わりに精度は 7〜8 割」という位置づけになります。

**Q19. いちばんのリスクは何か。**
未知の要件への汎化です。学習で見ていない種別は 0 問で、この状態で「何でも解くエージェント」と呼ぶのは言い過ぎになります。主張は「学習した 20 種別の問題を解く専用エンジン」に絞り、対応種別を明示し、対応外の要件は判定して弾く形で出します。

**Q20. 今後 5 か月で最優先は何か。**
順に、(1) 20 種別すべてのデータで Gemma 4 を学習し直し専用エンジンとして固める、(2) 修復ループを組み込んでエージェントにする、(3) 対応 20 種別の範囲で封印問題を確保する、(4) 指示文を揺らした学習で交互最適化を再検証、です。4 者（研究者、製品、スポンサー、実装の視点）に出させた計画がこの順で一致しました（`next_steps_review.md`）。
