## 3. demo とは何か、GEPA が選んでいるのか

demo は「問題文 → 正解コード」の few-shot 例 2 件で、生成 predictor の指示文の後ろに毎回付きます。持ち込み可のテストに典型問題の解答例を 2 問持ち込む、という当日の比喩がそのまま当てはまります。解法も含めた完全なコードです。

選定は GEPA ではなく `train_gepa_v3.py` の `build_demonstrations` が行い、手順は次の通りです。

1. 過去の評価結果から、参照値に一致した（exact_match）自作コードを候補にする。
2. 作者が固定した優先番号 prob_001（単一機械ジョブ順序）と prob_021（基本 VRP）を先頭に置く。候補にない場合は残りの exact_match 問題を番号順で補う。
3. 先頭 2 件を取る。

GEPA は指示文だけを進化させ、demo には触りません。MIPROv2 は demo の組み合わせも探索しますが、GEPA にその機能はありません。当日「LLM が選んでいるはず」という推測がありましたが、この構成では作者の固定です。

確認の過程で、**再学習 GEPA の demo が Phase E と違っていた**ことが分かりました。候補プールにする評価結果ファイルに prob_021 のレコードがなく、穴埋めで prob_006（会議室割り当て、スケジューリング_整数計画）が入っています。Phase E、compact、modular、before + demo の 4 条件は prob_001 と prob_021 のままなので、再学習 GEPA だけ demo が 1 件違い、指示文だけの比較になっていません。報告書 18 章とスライドの「demo は Phase E と同じ」は誤りで、訂正します。

## 6. スコアの式

採点は 3 段です。生成 140 問の評価では、既知最良値 b を参照値 r で初期化しているので、実質的に c / r の関数になります。c は解から再計算した目的値（最小化に統一）です。

**第 1 段: 失敗時の固定値**

| 状態 | score |
|---|---:|
| コードが出ない（gen_error）、構文・import・KeyError など | −0.5 |
| 実行時間超過 | −0.3 |
| その他の実行時例外、ソルバーが解を見つけない | −0.2 |
| 制約違反（部分点なし） | 0.0 |
| 制約の一部を満たす | min(0.3 × 充足率, 0.5) |
| 形が不正で目的値を計算できない | 0.1 |
| 参照値の 5% 未満（空解の疑い） | 0.3 |

**第 2 段: 実行可能な解の得点**

```
ρ = b / c
base = clip(2(ρ − 0.5), 0, 2)         # c = r で 1.0、c = 2r で 0
if |c − r| < 1e-6:  base = max(base + 0.2, 1.5)                         # 参照と一致
elif c < r:         base = max(base + min(0.5, 0.2 + 0.3(r − c)/r), 1.5) # 参照より良い
if c < b:           base += 0.15
if 1 < ρ ≤ 1.1:     base += 0.05 (ρ − 1) / 0.1
score = min(base, 2.5)
```

**具体値（生成 140 問）**

| 結果 | score |
|---|---:|
| 参照（厳密最適）と一致 | 1.5 |
| 10% 悪い | 0.82 |
| 50% 悪い | 0.33 |
| 2 倍以上悪い | 0.00 |

生成 140 問の参照解は厳密最適なので、1.5 が実質の上限です。平均 1.44 は「140 問中 133 問が 1.5、残り 7 問が失敗か部分点」という内訳で、平均値より正解数で見るほうが実態に合います。当日のご指摘どおり、以後の報告は正解数を併記します。

## 8. メトリックに「反省の方向」を書いているか

書いています。GEPA が反省 LM（Qwen3.8）に渡す文章は 2 層です。

**第 1 層: GEPA 本体の反省テンプレート（既定のまま）**
現在の指示文と、minibatch 3 問の「問題文・生成コード・feedback 文」を渡し、次の指令で新しい指示文を書かせます。原文の要点は「入力形式を特定しタスクを推定せよ」「**タスクに関するニッチでドメイン固有の事実をすべて指示文に含めよ**」「汎用戦略があればそれも含めよ」です。長さや一般化の指示はありません。指示文が仕様書化するのはこの一文の帰結です。

**第 2 層: このリポジトリの feedback 文（`src/gepa_feedback_v3.py`）**
採点結果の状態ごとに 14 分岐あり、「診断 + ACTION + HINT + Score」の形です。例を挙げます。

- 構文・キー誤り: 「instance.keys() を先に調べ、正確なキーを使え。説明文の変数名を仮定するな」
- 制約違反: 「容量、時間窓、順序、被覆を確認。すべてを丁度 1 回割り当てよ」
- ソルバー失敗: 「greedy に切り替えよ。OR-Tools を直そうとするな」
- 参照より悪い: 「greedy なら 2-opt を足せ。ソルバーなら時間を増やし warm start を入れよ」
- 種別別 HINT: 7 種別に手法提案（VRP は RoutingSolver、単一機械は EDD/Moore/DP など）。他の 20 種別は汎用文

第 2 層が「どう直すか」を毎回書き、第 1 層が「固有事実を全部入れよ」と命じるので、修正案がそのまま指示文に転写されます。方向を変える手段は 3 つあり、どれも未着手です。

1. 反省テンプレートの差し替え（`gepa_kwargs={"reflection_prompt_template": ...}`）。「複数問題に共通する失敗原因だけを一般則として書け」「N 文字以内」などを書ける。
2. `instruction_proposer` の自作。長さ超過を機械的に拒否できる。
3. feedback 文から ACTION を削り、「何が悪かったか」だけにする。

## 9. 再学習は 1 ループか。何度も回すべきか

「1 回の GEPA 実行」を 1 ループと数えれば 1 ループです。ただし GEPA の内部では 536 反復（minibatch 3 問の提案と採点）と 48 回の検証 13 問全評価を回しています。

もう 1 回回しても改善しない理由がはっきりしています。**検証 13 問が反復 152 で満点 1.5 に達して飽和**し、残る 384 反復は採否の信号を得られませんでした。同じ設定で続けても同じです。効くのは次の変更で、回数ではありません。

- 検証集合を飽和しないものにする（生成問題を混ぜる、厳密最適との差を連続値で採点する）。
- 反省の方向を変える（8 節）。
- 雛形を学習用と評価用に分け、見ていない種別への効果を直接測る。

## 10. 学習 11 時間を短くできるか

内訳は、生成 Qwen3.6 が 64k 枠で 1,920 rollout を解く時間と、反省 Qwen3.8 が 536 回指示文を書き直す時間です。設定は breadth 6 × depth 8 = 48 回の全評価、minibatch 3、候補評価 8 並列、検証 13 問です。

- 反省 LM を Qwen3.6 に替える。Qwen3.8 の思考の長さが反省側の時間を支配しています。

ご指摘の「検証数を減らす」は 13 問がすでに少ないので、減らすより飽和しない集合に替えるほうが効きます。

## 11. GEPA は単調に良くなるのか、非単調か

**検証集合の上では単調、ホールドアウトの上では非単調**です。

GEPA は候補ごとに検証 13 問の問題別スコアを持ち、Pareto 前線に残る候補から親を選びます。新候補は minibatch で親以上のときだけ全評価に進み、最後に検証平均が最高の候補を返します。返す候補は単調に選ばれますが、「ある問題を直す修正が別の問題を壊す」ことは提案の段階で起きており、Pareto 前線がそれを個別に保持します。

ホールドアウトでは出っ込み引っ込みが実際に出ています。

| モデル | 比較 | 改善した問題 | 悪化した問題 | 正解 → 不正解 |
|---|---|---:|---:|---:|
| Qwen3.6 | before → Phase E | 12 | 14 | 12 |
| Qwen3.6 | compact → 再学習 GEPA | 8 | 7 | 6 |
| Qwen3.6 | compact → modular | 7 | 14 | 14 |
| Qwen3.8 | compact → 再学習 GEPA | 18 | 10 | 8 |
| Qwen3.8 | compact → modular | 18 | 19 | 18 |

再学習 GEPA で新たに落ちた 6 問（Qwen3.6）は、CP-SAT の制約 1 行の誤りや LP の添字ミスで、指示文が直接壊したというより「同じモデルが同じ問題を別の書き方で解いて外した」揺れです。追加した規則が邪魔をした例は modular に多く、分野補足を付けた条件が 14 問の正解を落としています。

「マイナスをゼロにする修正ばかりでプラスにならない」というご懸念については、この問題集ではむしろ逆で、正解の 1.5 が上限なので伸ばせる余地が最初から小さいことが本質です（13 節）。

## 14. 問題が簡単すぎないか。採点の分解能を上げられるか

ご指摘のとおりです。生成 140 問は Fable で 138 問、特化 4B で 138〜140 問が正解で、上限に張り付いています。採点も「参照と一致で 1.5、それ以外は急減」でほぼ 2 値です。

分解能を上げる案を 3 つ挙げます。

1. **厳密解が 30 秒で出ない規模の instance を混ぜる。** 現在は数個〜数十個の要素で、CP-SAT や全列挙で最適解が出ます。要素数を 1 桁上げると、ヒューリスティックの質が目的値の差として連続的に出ます。既知最適値（または下界）との相対差で採点すれば、今の式がそのまま使えます。
2. **実行時間と出力トークンを副指標にする。** 現状でも記録しており、SFT モデルが Qwen3.6 の 1/10 の出力で同じ正解数を出す、といった差はここで見えます。
3. **複合問題を足す。** 「充足させてからその中で最適化する」型は、変数の取り方と制約の形式化が問われ、当日のご指摘どおり DSPy が覚えているのはこの手前の部分です。

「解法のエレガントさ」を直接採点するのは、目的値が同じなら差が付かないので難しいと考えます。計算時間とコード長が代理になります。

## 15. SFT（蒸留）についての質問

**28 と 140 の意味**
元の 100 問のうち、instance を機械的に生成でき、かつ厳密ソルバーを書ける 28 問を雛形にしました。雛形ごとに 5 instance を生成したものが生成 140 問です。SFT の学習データは同じ 28 雛形から seed を分けて 40 instance ずつ生成し、Fable と Qwen の正解コードを実行して正解を確認した 6,619 対です。

**表の各行の意味**

| 行 | 意味 | 平均 | 正解 |
|---|---|---:|---:|
| SFT テスト 140 問 | 学習した 28 雛形の未知 instance。クリーン | 1.487 | 138 |
| 生成 140 問 | Qwen・Fable と同じ集合。教師コードの出自なので準汚染 | 1.504 | 140 |
| 雛形外 70 問 | 学習に種別ごと現れない問題 | 0.430（素の 4B は 0.602） | 18（素は 27） |

**LoRA はどの層か**
最終数層ではなく、全層の線形射影に rank 32、alpha 64 の adapter を入れています。対象は attention の q/k/v/o 射影、MLP の gate/up/down 射影、線形 attention の in_proj です。Gemma 4 12B では言語部 328 層に入りました。adapter は数百 MB で、推論時はベースに焼き込むのでモデルのサイズは変わりません。

**蒸留でモデルは小さくなるのか**
なりません。大きいモデルの正解を小さいモデルに追加学習する操作なので、4B は 4B のままです。「27B と同等の正解数を 4B で出せる」が成果で、「4B をさらに小さくする」ではありません。4B より小さい土台は試していません。

**土台を大きくすると雛形外の劣化は緩むか（会議後に確認）**
Gemma 4 12B を同じデータで学習しました。雛形内は 139/140 で 4B と同じ天井、雛形外 70 問は素の Gemma の 48 問から SFT 後 28 問に落ち、劣化は 12B でも同じでした。原因は教師データの狭さ（168 通りのコードを 6,619 対に展開）で、土台の規模ではないと判断しています。対策は雛形を増やすか、一般のコードデータを混ぜて忘却を抑えるか、雛形に当たるかを判定して SFT モデルと素のモデルを切り替えるか、の 3 択です。

## 16. Better Together（プロンプト最適化と微調整の併用）

試す価値はあると考えます。現在の SFT は system prompt に compact を固定して学習しており、「プロンプトを固定して重みを学習した」片側だけです。DSPy の BetterTogether は「プロンプト最適化 → その出力で微調整 → 微調整後モデルで再びプロンプト最適化」を交互に回します。

この問題集で試すなら順序は次になります。

1. SFT 4B（または Gemma 12B）を生成 LM にして GEPA を回す。教師は同じ検証済みコード。
2. ただし雛形内は満点に近く信号が出ないので、雛形外 70 問を検証集合にする。
3. 効果は「雛形外で素のモデルの水準（Gemma で 48 問）を回復できるか」で測る。

コード生成は Claude Code で回せるので、実験の障壁は GPU 時間です。

## 17. GLM 系モデルの候補

候補に入れます。当日聞き取れなかったので、正確なモデル id（Hugging Face の名前）を教えていただけると助かります。評価は Gemma 4 と Ministral 3 で使った zero-shot の手順（compact を system prompt、参照値なしの問題文、思考なし 6k 枠）がそのまま使え、212 問で 7 分程度です。vLLM が対応していれば同日に結果を出せます。思考が短くて正解が多いモデルなら、Qwen3.8 の枠切れ問題（7 節）を回避できるので、比較の価値は高いと考えます。もう一方の担当者と環境をそろえる件は、モデル id が決まり次第合わせます。
